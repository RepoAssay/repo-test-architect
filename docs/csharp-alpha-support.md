# C# Experimental Support

The C# adapter is experimental. Its bounded slices prove that one conventional SDK-style test project or one unique literal production/test project edge, including that pair amid unrelated projects, can flow through project detection, audit, ranking, planning, explanations, findings, stats, CLI/MCP-shaped calls, golden snapshots, and model-consistency checks without a C#-specific report format.

## Supported Boundary

| Area | Supported in this slice | Evidence or blocker boundary |
| --- | --- | --- |
| Project shape | Exactly one root SDK-style test `.csproj`, or one unique literal production/test edge using `Microsoft.NET.Sdk`, a direct derivative such as the Web SDK, or the bounded MSTest SDK; unrelated projects remain separate | Two valid test edges, overlapping aggregate roots, and non-SDK projects are not merged into one owner |
| Project-pair edge | The selected test project has exactly one literal repository-contained `ProjectReference` resolving to the selected production project; the production project has no project edges | Property-expanded, wildcard, absolute, escaping, missing, additional, reverse, ambiguous, and transitive edges block command selection |
| Inherited metadata | The nearest exact-cased, non-symbolic, repository-local `Directory.Build.props` may supply literal unconditional `<TargetFramework>` or `<TargetFrameworks>`, `<IsTestProject>`, and supported test-package `Include` declarations; project-local values retain bounded precedence | Imports, conditional relevant groups/items, property expansion, conflicting inherited/local framework properties, inherited project/compile items, and symbolic props paths block command selection |
| Central package versions | The nearest exact-cased, non-symbolic, repository-local `Directory.Packages.props` may supply one static `PackageVersion` per selected-project package; central enablement is a literal unconditional boolean in the project, build props, or package props, and a version may use one exact same-file literal property alias | Imports, conditions, repeated or missing versions, chained/unresolved properties, dynamic IDs, local `Version`/`VersionOverride`, global references, and symbolic paths block command selection |
| Package conditions | A project-local `PackageReference` or its `ItemGroup` may use a finite `$(TargetFramework)` predicate over declared literal targets: one comparison kind (`==` or `!=`), optionally joined by one boolean kind (`And` or `Or`), selecting a non-empty proper target subset | Conditional test infrastructure, inherited conditional central/test metadata, nested conditions, undeclared targets, mixed operators, parentheses, functions, configuration/OS properties, and arbitrary MSBuild expressions block command selection |
| Target framework | One static local or inherited `<TargetFramework>`, or one semicolon-delimited `<TargetFrameworks>` list with at least two unique literal values; every test target in a pair occurs literally in the production list | Conditions, property expansion, repeated declarations, invalid/empty/duplicate lists, and test targets absent from the production list block command selection; framework compatibility is not inferred |
| Source ownership | Default SDK compile ownership below the selected production project directory; collocated single-project source remains owned below the audit root | Test-project helpers are not candidates; `bin`, `obj`, dependencies, fixtures, and custom `Compile` graphs are excluded |
| Test project | `Microsoft.NET.Test.Sdk` or static `<IsTestProject>true</IsTestProject>` plus a supported framework package; alternatively, an xUnit MTP-v2 project with exact `xunit.v3.mtp-v2` and `Microsoft.Testing.Platform.MSBuild` 2.x-or-newer package references, or exact `MSTest.Sdk/4.x-or-newer` with an inline version or root `global.json` `msbuild-sdks` version | The native MTP paths additionally require an exact repository-root runner selection and a statically proven .NET 10+ command context; `<UseVSTest>true</UseVSTest>` and `<IsTestApplication>false</IsTestApplication>` are excluded from MSTest command ownership |
| Frameworks | xUnit `[Fact]`/`[Theory]` through `xunit`, `xunit.v3`, or the bounded `xunit.v3.mtp-v2` path; NUnit `[Test]`/`[TestCase]`/`[TestCaseSource]`; and MSTest `[TestMethod]`/`[DataTestMethod]`; an MSTest `[ExpectedException]` upgrades exactly one sole direct top-level source call, exact xUnit/NUnit/MSTest `Assert.Throws*`/`Assert.Catch*` single-expression lambdas credit one direct source call, selected NUnit/MSTest projects recognize static `CollectionAssert.*`/`StringAssert.*`, and selected NUnit projects recognize `ClassicAssert.*` through an exact `NUnit.Framework.Legacy` import, exact owner alias, or fully qualified owner | Package and runnable attributed-test evidence must agree; ambiguous, multi-statement, wrapped, captured, nested, block/helper-owned, deferred-lambda, custom-assertion, wrong-framework exception shapes, locally declared or source-owned `ClassicAssert` collisions, and specialized assertion owners without their selected framework/provenance do not upgrade usage |
| Command | `dotnet test <test-project>.csproj`; native xUnit MTP-v2 and MSTest.Sdk v4 use exact root `global.json` runner ownership plus either a literal .NET 10+ SDK pin or exclusively literal `net10.0`-or-newer test targets | Emitted only when project, edge, target, compile, test-runner, and ownership checks are complete; MTP v1, compatibility-mode flags, old or dynamic MSTest SDK versions, inferred/transitive hosts, mixed pre-net10 targets without an SDK pin, and other framework integrations remain blocked |
| Direct evidence | Inside a runnable attributed test body, one uniquely owned class, record, or struct used through a top-level `Type.Method(...)`, `new Type(...)`, an exact local initialized with `new Type(...)`, or an exact `private readonly Type field` whose receiver is called by that test; when `using System;` is present, well-known root-type collisions require qualification or an exact alias to the unique source namespace | Test-local declarations, duplicate source types, comments, strings, characters, constructors/field initializers alone, ordinary helper bodies, nested local functions, deferred lambdas, unqualified `System` collisions, explicit `System.Type` references, and unused names contribute nothing |
| Test-helper evidence | One runnable test may directly call one unique same-class `private static` helper whose top-level body contains exactly one source `Type.Method(...)` or `new Type(...)` call; this emits `csharp-test-helper` as indirect evidence with called/asserted entrypoint usage, and direct evidence in the same test file wins | Uncalled, public/instance, overloaded, generic, expression-bodied, ambiguous multi-source, nested, lambda-owned, locally shadowed, cross-class/file, receiver, helper-chain, and helper-return flow remains excluded |
| Receiver/result usage | A stable concrete local or exact private readonly concrete test field can prove `value.Method(...)`; fields use exact inline `new()`/`new Type(...)` or one assignment in the class's sole parameterless constructor. A direct `Type.Method(...)`/`new Type(...)` result, receiver-call result, or one top-level inline `out var` consumed by `Assert.*`, `.Should(...)`, selected NUnit/MSTest `CollectionAssert.*`/`StringAssert.*`, or provenance-backed NUnit `ClassicAssert.*` is `asserted` | Receiver/result reassignment, interface-typed construction results, predeclared/explicitly typed/multiple/nested `out` declarations, `ref`/`out` forwarding, mutable/static/interface/property/inherited/helper/partial field identity, multiple constructors, local shadows, nested local functions, deferred lambdas, and deeper result flow are rejected |
| Naming evidence | A unique `Foo.cs` to `FooTest.cs`/`FooTests.cs`/`FooSpec.cs`/`FooSpecs.cs` fallback | Used only when the same test has no stronger direct evidence for that source file |

The adapter classifies branching and fallible behavior, service and external boundaries, parsers, validators, calculators, formatters, mappers, repositories, controllers, and clients. Generated files, application startup wiring, data-only models, and interfaces are deferred with explicit reasons rather than promoted as direct test targets.

## Checked Fixtures

`examples/csharp-sdk-xunit-basic` is a collocated SDK-style xUnit test project targeting `net10.0`. It contains one directly asserted `PriceParser`, one untested branching `CheckoutService`, and one deferred data-only `CheckoutRequest`. The fixture uses the package versions emitted by the installed .NET 10.0.302 SDK template and passes:

```sh
dotnet test CheckoutRules.Tests.csproj
```

The ordinary adapter audit does not execute `dotnet`, MSBuild, NuGet restore, source generators, target-repository code, or tests. The reported command is deterministic repository guidance; native execution is a fixture-validation gate performed separately.

`examples/csharp-sdk-project-pair` contains `src/CheckoutRules/CheckoutRules.csproj` and `tests/CheckoutRules.Tests/CheckoutRules.Tests.csproj` connected by one literal relative `ProjectReference`. Its production project targets `net8.0;net9.0;net10.0` while its test project targets `net10.0`, locking literal target-superset ownership without compatibility inference. It keeps test helpers outside the candidate set, carries direct asserted evidence from a static call to `DiscountCalculator`, follows an exact `CheckoutService` local receiver through one result into xUnit, and defers the data-only `CheckoutRequest`. The fixture passes:

```sh
dotnet test tests/CheckoutRules.Tests/CheckoutRules.Tests.csproj
```

`examples/csharp-sdk-unique-pair` adds unrelated Worker and benchmark projects around one Pricing/Pricing.Tests edge. Its root `Directory.Build.props` supplies the shared static target framework, while `Directory.Packages.props` supplies the selected test project's versions through literal entries and one same-file property alias. Detection collapses only the exact pair, direct audit excludes unrelated source, and the fixture locks both props setup signals, the central-package convention, command, and asserted inline `out var` result from a `private readonly` target-typed field through golden and model-consistency artifacts. It passes:

```sh
dotnet test tests/Pricing.Tests/Pricing.Tests.csproj
```

## Explicit Exclusions

The first slice does not claim:

- `.sln` or `.slnx` ownership
- more than one selectable production/test project edge, transitive project edges, multiple references, or solution-wide ownership
- `Directory.Build.targets`, imported SDKs, imported or chained props, conditional relevant metadata, property-expanded inherited metadata, or evaluated MSBuild graphs
- custom, removed, or explicitly included `Compile` items
- conditional, property-expanded, repeated, invalid, empty, or duplicate target-framework lists; compatibility inference between different target framework monikers
- conditional, imported, chained, repeated, overridden, global, or symbolic central package metadata; package conditions outside the finite project-local target predicate; conditional test infrastructure; custom test adapters; MTP v1 or VSTest compatibility mode; native MTP layouts other than the exact xUnit v3 MTP-v2 or MSTest.Sdk v4 hosts; old, dynamic, conditional, or externally inferred MSTest SDK versions; MSTest helper-library ownership; or other framework/package versions inferred through external properties
- namespace, alias, or partial-type joining beyond the exact supported source and NUnit `ClassicAssert` aliases; generic-type, overload, target-typed construction outside the exact supported field shape, receiver/result reassignment, mutable/static/interface/property/inherited/helper field identity, helper-return, cross-file/class, chained, receiver, or ambiguous helper flow, ambiguous/wrapped/multi-statement expected-exception flow, block/captured/nested/custom exception assertion lambdas, predeclared/explicitly typed/multiple/nested `out` declarations, `ref`/`out` forwarding, other nested local-function or deferred-lambda flow, mock, reflection, source-generator, or dependency-graph resolution
- cross-project evidence outside the one verified production/test edge, or any transitive evidence

Literal pair selection now covers a unique test edge amid unrelated projects without claiming solution ownership, Sharp Cast proves exact test-class field receivers initialized through target-typed `new()` plus one stable inline `out var` result, Glob proves bounded nearest-file inherited metadata, EFCore.CheckConstraints proves bounded central versions, ErrorOrAspNetCoreExtensions proves literal multi-target ownership, S7.Net proves finite project-local target package predicates plus stable direct type-call results, the official NUnit samples prove repository-wide routing across six collocated independent test owners, StepUpLogging proves repository-owned native xUnit MTP-v2 command selection, and usbipd-win proves MSTest.Sdk v4 pair and runner ownership without weakening the MSBuild command boundary. Broader MSBuild evaluation, framework compatibility inference, other MTP framework integrations, conditional or overridden central versions, and explicitly typed or multi-output `out` flow remain pressure only when another pinned repository justifies them.
