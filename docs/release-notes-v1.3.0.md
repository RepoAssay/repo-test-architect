# Repo Test Architect 1.3.0

Status: **prepared, not yet published**. This document is updated with the release commit, publication times and verification links once the version is on npm, in the Official MCP Registry and on GitHub.

## Summary

A compatible minor release carrying the Swift and Kotlin/JVM fixes from the first runs on private product monorepos. The Swift adapter no longer suggests `swift test` for packages that need UIKit, WatchKit or TVUIKit, and it links `Type+Feature.swift` extension files to the tests that exercise their members. The Kotlin/JVM adapter indexes top-level extension functions, counts Android instrumented tests as evidence of their own kind, resolves what instrumented tests can see separately from unit tests, and describes the Android boundary accurately. The runtime dependencies hono and @hono/node-server are updated.

The 20 MCP tool names, the CLI commands, configuration and artifact schemas are unchanged except for one added value in the `audit/v1` evidence-kind enum. Audit results change on affected repositories; the changes are listed under [Compatibility Notes](#compatibility-notes).

## Why

Run through Claude Code against a Swift application with about eighteen local packages and against a multi-module Android application, the 1.2.0 adapters produced eight issues within two runs. Four are fixed here (#311, #315, #316, #317); #309 shipped in 1.2.0; #310, #312 and #318 are open design questions. All of them are shape problems the public validation corpus did not contain, which is recorded in the [product-monorepo validation plan](product-monorepo-validation.md) together with the repositories that close the gap for every adapter.

## Correctness Fixes

- **`swift test` is withheld for packages that cannot build on the macOS host** (#311, PR #323). In the SwiftPM branch of command selection, an import of UIKit, WatchKit or TVUIKit in a source the package compiles withholds `swift test` and emits one blocker naming the matching destination shape, for example `xcodebuild test -destination 'platform=iOS Simulator,name=<device>'`, without guessing a device. Only compiled files count: owned sources and test sources, minus files an `exclude` or an explicit `sources` list leaves out, for test targets too. Import declarations with attributes, access levels and kinds (`@preconcurrency public import struct UIKit.UIColor`) are recognised; comments and string literals, including multiline literals, are masked. Imports inside `#if` branches that are provably inactive on macOS do not count: conditions are evaluated three-valued with `!`, `&&`, `||` and parentheses over `os(...)`, `canImport(...)` and `targetEnvironment(...)`, a later `#elseif` or `#else` branch is unreachable once an earlier branch was provably active, and anything unresolved (`#if DEBUG`, its `#else`, an unknown module or a `canImport` submodule) keeps the import and withholds the command rather than guessing. A `platforms:` list naming only iOS does not withhold the command on its own, because SwiftPM platform entries declare minimum deployment versions rather than the buildable set. Bazel and Xcode command selection are unchanged, and auditing is unaffected: the package's sources stay covered or untested exactly as before.
- **`Type+Feature.swift` extension files are linked to their tests** (#317, PR #321). The adapter credited an instance extension member only when a test called it on a constructor result directly. It now also credits a source-file-unique member called on a local bound directly to a constructor result (`let url = URL(string: "…")!` then `url.adding(queryItem:)`), including through `Type(...)!.member()` and `Type(...)?.member()`. The binding is dropped whenever the test could mean something else: the constructor result is chained into another call, a type annotation names a different type, the local is declared or assigned more than once, or the same name appears as a parameter of any form, a closure parameter (including backtick-quoted ones), a loop or tuple binding anywhere in the file. An `init(label:)` declared in an extension is credited through its labeled call (`Activity(deepLink:)`) when no other initializer of the type shares that first label. `+` is removed from file-name keys, so `URL+Utils.swift` gains naming evidence from `URLUtilsTests.swift` when no member call is proven and no other source normalises to the same name. When one test exercises several symbols of the same source file, the reported usage is the strongest (asserted over called over referenced) rather than whichever symbol sorts first.
- **Kotlin top-level extension functions are indexed as source symbols** (#315, PR #320). Files holding only top-level extension functions (`fun LinkDto.asLink()`, `fun ImageDto?.asImage()`, `fun com.example.api.ChannelDto.asChannel()`, `fun <T : Any> List<T?>.compacted()`) were reported as untested although same-package tests call them. The function pattern now accepts a receiver with dotted segments, generic arguments and an optional `?`; only file-scope declarations count, so member extensions inside classes stay out, and an extension name declared on different receivers in more than one file of the same package is withheld as ambiguous unless the file also declares a type or plain function of that name. Evidence matching is unchanged. The unrelated same-basename fallback from the issue is deliberately not implemented.
- **Android instrumented tests count as instrumented evidence** (#316, PR #324). `src/androidTest` is now a conventional test source set over `src/main`. A symbol reference from an instrumented test yields `android-instrumented-symbol-reference` evidence with the same strength and usage rules as `jvm-symbol-reference`, so classes tested only on a device are covered-but-risky with a distinguishable kind instead of missing coverage. Instrumented tests resolve cross-module visibility from the module's `api`, `implementation` and `compileOnly` project dependencies plus `androidTestImplementation`, `androidTestApi` and `androidTestCompileOnly`, never from `testImplementation`; unit tests see the main and `test*` configurations as before. The Android blocker now states what holds: unit tests under `src/test` count as evidence, instrumented tests count as instrumented evidence, build variants, flavors, Robolectric semantics and device execution are not modeled, and the suggested command runs unit tests only. The new kind is declared in the `audit/v1` schema, the TypeScript evidence union and the adapter conformance table.

## Dependencies

- hono 4.13.18 and @hono/node-server 2.1.8 (PR #322, superseding Dependabot #319). No API or behavior change in this package.

## Compatibility Notes

- **Swift commands change on UIKit, WatchKit and TVUIKit packages.** For such packages the project's `testCommand` is now undefined, `blockers` gains one entry, `confidence` is no longer `high`, and `verificationCommands` in `repository-review/v1` no longer list `swift test` for them. Consumers that ran the suggested command for these packages must select an `xcodebuild` destination themselves.
- **Swift candidates and evidence move.** Extension files that were `missing-coverage` become covered when a test reaches their members through a bound local, a labeled extension initializer or a matching file name, and existing `existingTestEvidence` entries may report a stronger `usage` than before. Rankings and plan items change accordingly on affected repositories.
- **Kotlin candidates move.** Files holding only top-level extension functions gain evidence and leave the untested list; nothing that was covered becomes uncovered.
- **New evidence kind.** `android-instrumented-symbol-reference` is added to the `existingTestEvidence[].kind` enum of `audit/v1`. Artifacts written by 1.2.x still validate against the 1.3.0 schema. Consumers that validate audits against a vendored copy of the 1.2.x schema must update that copy before auditing Android modules with instrumented tests.
- **Android blocker text changed.** The blocker that began "Android unit and instrumentation source sets are outside the supported JVM module boundary" now begins "Android modules are audited with JVM conventions:". Consumers matching the old text must update. Android modules also gain covered-but-risky candidates for classes tested only from `src/androidTest`, and cross-module instrumented evidence requires an `androidTest*` or main configuration dependency.
- No field was removed or renamed in any artifact, descriptor or CLI output. Golden fixture snapshots are unchanged.

## Installation And Upgrade

Node.js 20 or newer is required:

```sh
npx --yes repo-test-architect@1.3.0 doctor
npx --yes repo-test-architect@1.3.0 review .
npx --yes repo-test-architect@1.3.0 analyze .
npm install --global repo-test-architect@1.3.0
```

For MCP clients, use `npx --yes repo-test-architect@1.3.0 mcp` or the unversioned package argument, which follows npm `latest`. CLI binary names and client configuration structure are unchanged. Clients that pinned `1.2.0` must update their package argument to receive these fixes.

## Verification

Each change has regression tests: the Swift command table (production and test imports of each framework, import modifiers, masked comments and strings, guarded imports with `||`, `&&`, negation, trailing `#else`, submodule and unknown `canImport` arguments, excluded and omitted test files, Bazel precedence), the extension-member crediting cases with isolated negative fixtures for every shadowing shape, the Kotlin receiver forms with cross-file ambiguity, and the Android instrumented cases including schema validation and both directions of dependency visibility. All five pull requests (#320, #321, #322, #323, #324) passed the Linux `pr-gate` and Windows portability checks plus an independent model review before merge, and the macOS Swift check ran and passed on the Swift pull requests. Golden snapshots were unchanged. The release commit passed the full local release gate (1,733 tests) and strict distribution checks; the three-OS release matrix and the clean install from the public registry are recorded after publication.
