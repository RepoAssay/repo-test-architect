# JavaScript/TypeScript Product-Monorepo Validation Hunt: cal.com

This report records the first product-monorepo hunt pass (#325) for the JavaScript/TypeScript adapter. [`calcom/cal.com`](https://github.com/calcom/cal.com) was shallow-cloned at commit `ef7954d16ab50882ca2f263c551537115b8a8bb1` (upstream commit of November 11, 2026) and audited with Repo Test Architect 1.3.0 from the repository checkout at `8c840ba`. The auditor's `review --format json --limit 50` and `analyze --format json` commands were run from the repository root; no dependency installation, build, test or application code of cal.com was executed.

## Shape

cal.com is a Turborepo monorepo with Yarn workspaces: `apps/*`, `apps/api/*`, `packages/*`, `packages/embeds/*`, `packages/features/*`, `packages/app-store`, `packages/app-store/*`, `packages/platform/*`, `packages/platform/examples/base` and `example-apps/*`, 119 `package.json` roots in all. Unit tests run from the repository root: the root `test` script is `TZ=UTC vitest run` and `vitest.workspace.ts` declares named projects with include globs such as `packages/**/*.{test,spec}.{ts,js}`, `apps/**/*.{test,spec}.{ts,js}`, `packages/features/**/*.{test,spec}.tsx` and per-app-store globs. Most packages declare no test runner, test script or runner configuration of their own. `apps/web` and the embed packages carry Playwright end-to-end suites; `apps/api/v2` is a NestJS application with Jest and Supertest.

## Findings

1. **Root-owned runner configuration is not inherited (should-fix, adapter gap; #329).** 107 of 119 packages are blocked for having no package-local test framework or script, although the root `vitest.workspace.ts` runs their tests. 18 of those packages hold 319 checked-in test files (`packages/features` 198, `packages/trpc` 33, `packages/ui` 32, `packages/app-store` 12, `packages/features/auth` 10, `packages/app-store/salesforce` 8, `packages/emails` 6, `packages/app-store/stripepayment` 5, and others). The [support matrix](javascript-typescript-alpha-support.md) accepts inherited runner configuration only when the package's own script selects it with `--config`; cal.com has no such scripts, so the boundary is applied as documented, but the outcome misdescribes the repository: packages whose tests run on every CI build are reported as lacking test infrastructure. Proposal: when the owning workspace root declares a supported runner and a workspace or projects configuration whose literal include globs cover a package, report the framework for that package with a `workspace-inherited runner` convention and the root command (`yarn test`, or `npx vitest run --project <name>` when the project is named), and keep withholding when the globs are computed.
2. **A stale `jest.config.json` selects `npx jest` at high confidence (false command; #330).** `packages/lib` carries a `jest.config.json` (`testRegex: ".*\\.spec\\.ts$"`, `ts-jest` transform) but no `jest` dependency and no test script, and all 45 of its test files import from `vitest`; the repository runs them through the root Vitest workspace project `@calcom/lib`. The adapter reports `testFrameworks: ["jest"]`, `testCommand: "npx jest"`, confidence `high`. Running that command would fail. Proposal: a runner configuration file alone should not select the framework when the package lacks the runner dependency and its test files import a different runner; prefer dependency plus imports, and otherwise withhold the command with a `command` diagnostic naming the conflicting configuration.
3. **Package-root source files are not audited (should-fix; #331).** `packages/lib` keeps 125 `.ts` sources (129 with `.tsx`) at the package root beside 24 colocated `*.test.ts` files (`array.ts`, `CalendarService.ts`, `CalEventParser.ts`, `crypto.ts` and more, each with a sibling test), yet its audit reports 0 untested, 0 covered and 0 skipped targets. The adapter audits sources under its conventional source roots (`src/`, `source/`, `lib/`) or files named by a declared `package.json` entrypoint (`main`, `module`, `exports`, `bin`), and `packages/lib` has neither, so the files are never candidates. A minimal reproduction (a `package.json` with a Vitest script, `slugify.ts` with branching and a throw, `price.ts`, and `slugify.test.ts`, all at the package root) also yields no targets. Proposal: audit `.js`/`.ts` sources at the package root when the package has no conventional `src/` or `lib/` directory, excluding configuration files by name pattern, and record the rule in the support matrix.
4. **Blocker severity at scale (#312).** 214 of the 452 high-severity findings are blocked-project findings for missing package-local infrastructure, and they outrank every coverage gap in the review. #312 proposes replacing the two blockers with one finding per package; PR #333 implements that as one medium coverage-gap finding, and once #329 lands it would apply only to the packages the root workspace does not run.

## What Held

All 119 roots were detected and audited once, with the nested `apps/api/v2`, `packages/embeds/*`, `packages/features/*` and `packages/app-store/*` packages owned independently. Package-local runners were recognised where declared: Playwright and React Testing Library in `apps/web` (34 untested, 7 covered), Playwright in `packages/embeds/embed-core` (5 untested, 16 covered), Jest and Supertest in `apps/api/v2` (329 untested, 28 covered; its `*.e2e-spec.ts` suites exercise controllers over HTTP and are outside the evidence boundary by design), Vitest in `packages/app-store/closecom` and `packages/testing`, and Jest in `packages/platform/*`. The bounded review stayed at 249 KB for 119 projects at `--limit 50`, and both commands completed in under ten seconds.

Stability and performance: pending (three repeated measurements after the fixes). The case is pinned as the adapter's `product-monorepo` corpus role once the scorecard passes.
