# Repo Test Architect 1.4.0

Status: **prepared, not yet published**. Publication status is recorded here and in the [publication ledger](distribution-metrics.md) once the release commit is published.

## Summary

A compatible minor release that separates what limits an audit into structured diagnostics, reads Xcode scheme test actions and accepts an explicit scheme selection, links tests in sibling Swift packages as evidence, and records the first three public product-monorepo validation passes. For the Swift, Kotlin/JVM and JavaScript/TypeScript adapters, projects without a test target are no longer "blocked": they are audited in full at medium confidence with one coverage-gap finding that names the missing test target (the other adapters' findings follow the same classification; see [Compatibility Notes](#compatibility-notes)). A withheld test command is a finding of its own kind (`command-withheld`) and no longer lowers confidence. On Xcode applications with several shared schemes the adapter reads each scheme's test action, picks the scheme when the choice is provable and otherwise withholds the command while listing the candidates, which a new `swiftSchemes` input (CLI `--swift-scheme`) resolves. Tests that live in another local Swift package are linked to the sources they call or assert on, and reported as misplaced coverage with the owning package named.

The 20 MCP tool names and the CLI commands are unchanged. One optional input (`swiftSchemes`, CLI `--swift-scheme`) is added to the scan tools, and the artifact schemas gain only optional fields and one category value. Audit results change on affected repositories as listed under [Compatibility Notes](#compatibility-notes).

## Why

The 1.3.0 notes left three design questions from the first product-monorepo runs open: #310 (several shared Xcode schemes blocked the root project), #312 (a package without a test target was reported as a high-severity blocker rather than a finding) and #318 (tests in a sibling package were ignored). This release closes all three, and the first public product-monorepo hunt (cal.com) confirmed the #312 shape at scale: 107 of 119 workspace packages were blocked twice over for having no package-local runner. The Swift and Kotlin/JVM changes shipped only after public hunts on `Dimillian/IceCubesApp` and `android/nowinandroid`, whose reports are linked below; the Ice Cubes pass found one issue in the new cross-package rule (#338), fixed here before release.

## Audit Diagnostics

**Structured diagnostics separate bounded audits, withheld commands and missing tests** (#312, PR #333). Adapters describe what limits an audit with `profile.diagnostics` entries (`code`, `scope`, `severity`, `message`) in three scopes: `audit` for a bounded (medium) or untrustworthy (high) source or evidence audit, `command` for a withheld test command, and `test-infrastructure` for a project with no test target, framework or runnable tests. `profile.blockers` stays the string projection of the `audit` and `command` scopes. Findings map audit diagnostics to `blocked-project` with the diagnostic's severity, command diagnostics to the new `command-withheld` category (medium), and a project's test-infrastructure diagnostics to one `missing-coverage` finding (medium; low on auxiliary roots) with a `code` such as `missing-test-target`. `profile.confidence` now means confidence in the source and evidence audit and is lowered only by audit diagnostics; a project with no recognised framework is capped at medium. The Swift, Kotlin/JVM and JavaScript/TypeScript adapters emit diagnostics natively; the other adapters keep their blocker strings and their own confidence rules, and findings classify those strings through a finite table of the known messages read together with the profile's frameworks and test locations, so saved 1.3.x artifacts and unmigrated adapters produce the same finding categories. The Markdown report gains a "Test Infrastructure" section when such diagnostics exist.

## Swift

- **Xcode scheme selection reads test actions and accepts an explicit selection** (#310, PR #334). Only shared schemes whose `TestAction` is statically runnable are eligible for `xcodebuild test -scheme`: the action must reference a test plan whose `.xctestplan` file is checked in, or list an enabled testable. Among eligible schemes a unique workspace-name match wins, then a unique project-name match, then the sole eligible scheme; anything else withholds the command as the `ambiguous-xcode-scheme` command diagnostic listing the candidates with their container when a name is shared. `swiftSchemes` on `audit_repo`, `audit_projects`, `analyze_repository`, `review_repository` and every artifact-consuming tool's `repoRoot` path (keyed by detected project root, `"."` for a lone root) and CLI `--swift-scheme <root>=<scheme>` (or `<scheme>` alone for a single-project command, repeatable) name the scheme explicitly. A selection that is not a shared scheme, declares no test action, or exists in several containers withholds the command with `invalid-xcode-scheme-selection` instead of being replaced; a key naming an undetected root is a usage error. The applied selection is recorded as the setup signal `xcode scheme selected by input`. Test-plan lookup uses the selected scheme's own file.
- **Tests in sibling Swift packages count as evidence and are reported as misplaced coverage** (#318, PR #335; #338, PR #339). After a repository scan has audited every project, tests that live in another detected Swift project are linked to the targets they exercise when the test imports a module that exactly one scanned project declares and calls or asserts on a symbol of the target's source file (a type-position mention links only inside a package). Evidence keeps `swift-symbol-reference` with the usual strength and usage and a `testPath` relative to the audited project root that escapes it (`../B/Tests/BTests/FooTests.swift`). Targets covered only this way move from `untestedCandidates` to `coveredButRisky`; the placement analysis reports the test as `misplaced-coverage` owned by the other project with the audited project as suggested owner, and the redundant weak-coverage finding is omitted for external-only coverage. A symbol name the test's own project declares or qualifies with another module is never credited; a module name declared by several scanned projects is not linked and, when a third project's test imports it, each declaring project records the medium audit diagnostic `ambiguous-cross-project-module`. The pass computes all links first and applies them second, and a failure of the pass leaves every audit as produced. Lone-root `audit_repo` never looks outside its root.

## Compatibility Notes

- **Projects with no tests are no longer blocked.** For the Swift, Kotlin/JVM and JavaScript/TypeScript adapters a project with no test target, framework or runnable tests now has `blockers: []`, `confidence: "medium"` (was `low`) and one `missing-coverage` finding with a `code` (`missing-test-target` for Swift and Kotlin/JVM, `missing-test-framework` for JavaScript/TypeScript) instead of two high-severity `blocked-project` findings. `summary.blockerCount` and the `blockers` list of `repository-review/v1` shrink accordingly. For the other seven adapters `blockers` and `confidence` are unchanged, but their known blocker strings are classified the same way for findings: a project with no tests yields one medium `missing-coverage` finding (`code` `missing-tests`, `missing-test-command`, `missing-test-framework`, or `missing-test-infrastructure` when several messages apply) instead of high-severity `blocked-project` findings, and withheld-command messages yield `command-withheld` findings. `summary.blockedProjectCount` and `highSeverityCount` therefore shrink for every adapter, while `blockerCount` and the review `blockers` list shrink only for the three migrated adapters. Consumers that treated every blocker as "do not audit" should read `profile.diagnostics` and act per scope.
- **Withheld commands are `command-withheld` findings** (medium) rather than `blocked-project`, and no longer lower confidence for the three adapters that emit diagnostics (a UIKit package whose `swift test` is withheld is now `high` confidence); the other adapters keep their confidence rules. Consumers matching the `blocked-project` category for withheld commands must add `command-withheld`.
- **Additive schema changes.** `profile.diagnostics` is optional in `audit/v1`; `command-withheld` is added to the category enums of `project-findings/v1` and `repository-review/v1` with an optional `categoryCounts` key; `code` is optional on findings. Artifacts written by 1.3.x validate against the 1.4.0 schemas. Consumers that validate against a vendored copy of the 1.3.x schemas must update that copy before reading 1.4.0 artifacts.
- **MCP descriptor and instructions.** The `tools/list` descriptors of the scan-capable tools gain the optional `swiftSchemes` input, and the server `instructions` text now says that a project whose profile diagnostics report only missing test infrastructure is fully audited.
- **Xcode commands change on multi-scheme containers.** Only test-capable schemes are candidates: a container with several shared schemes of which exactly one declares a test action now yields `xcodebuild test` where 1.3.0 withheld it, and a container whose sole shared scheme declares no test action no longer yields the command (it was accepted unread before). When several test-capable schemes remain and none is a unique workspace- or project-name match, the command is still withheld and the candidates still listed, but as a medium `command-withheld` finding with the `ambiguous-xcode-scheme` code and unchanged confidence (1.3.0: a high `blocked-project` finding with lowered confidence); the message keeps the "Multiple shared Xcode schemes" prefix, now shows the container for shared names and names `swiftSchemes`, and `swiftSchemes` or `--swift-scheme` resolves it.
- **Swift candidates and findings move across packages.** In repository scans, a source called or asserted on by a test in a sibling package becomes covered-but-risky with evidence whose `testPath` begins with `../`, and gains a `misplaced-coverage` finding naming the owning package. Lone-root audits are unchanged.
- **Golden snapshots changed** in PR #333: the JavaScript/TypeScript, Kotlin/JVM and Swift fixture audits (31 of 58) gain `profile.diagnostics`, the other adapters' fixtures are unchanged, and the `node-no-tests-yet` and `vapor-service-tests` fixtures change as described above. No field was removed or renamed in any artifact, descriptor or CLI output.

## Installation And Upgrade

Node.js 20 or newer is required:

```sh
npx --yes repo-test-architect@1.4.0 doctor
npx --yes repo-test-architect@1.4.0 review .
npx --yes repo-test-architect@1.4.0 analyze .
npm install --global repo-test-architect@1.4.0
```

For MCP clients, use `npx --yes repo-test-architect@1.4.0 mcp` or the unversioned package argument, which follows npm `latest`. CLI binary names and client configuration structure are unchanged. Clients that pinned `1.3.0` must update their package argument to receive these changes.
